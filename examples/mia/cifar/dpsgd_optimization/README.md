# DP-SGD privacy-utility optimization on CIFAR-10

Finds the **utility-vs-privacy frontier** for DP-SGD on a small CIFAR-10 CNN by
*optimizing*, not sweeping. Optuna (Bayesian optimization) proposes each next
configuration of the four DP-SGD knobs from the results seen so far; every
configuration is trained and then attacked with **LeakPro's own RMIA attack**
(`leakpro.attacks.mia_attacks.rmia`) run through the normal LeakPro pipeline.

- **Knobs (searched jointly):** noise multiplier, clipping norm, learning rate,
  batch size.
- **Objectives:** maximize test accuracy, minimize RMIA **TPR @ FPR = 1%**.
- **Shadow models:** trained by LeakPro's `ShadowModelHandler` through the same
  handler and the same DP-SGD configuration as the candidate target, so every
  RMIA reference model mimics the target it attacks. This happens once per
  configuration — new configuration, new shadow models. One part of mimicry is
  a *split-size coupling*, not automatic: balanced shadow sampling trains each
  reference on `pop_size // 2` points, so `splits.pop_size = 2 * n_target` is
  deliberate and enforced — it is what makes the references' training-set size
  (and therefore their DP-SGD sampling rate `q = B/N` and step count) match the
  target's.

## How the pieces fit the library

Nothing about the attack lives in this example. The optimization loop is
`leakpro.optimization`:

- `optimize(objective_fn, knob_space, out_dir, n_trials)` — the Optuna search.
- `run_rmia_audit(handler_cls, audit_yaml)` — runs `LeakPro(...).run_audit()` and
  returns the RMIA `MIAResult`.
- `tpr_at_fixed_fpr(result, 0.01)` — reads TPR@1% from `MIAResult.fixed_fpr_table`.

This example provides only *training* (which LeakPro always leaves to the user's
handler): `dp_handler.py` defines `SmallCNN`, a `CifarDPHandler`, and one DP-SGD
training function used for **both** the target and the RMIA shadow models.

## Prerequisites

The run reads `examples/mia/cifar/data/cifar10.pkl`, which is **not in the
repository** (it is `.gitignore`d). Generate it with the CIFAR example notebook
(`examples/mia/cifar/cifar_main.ipynb`, the data-preparation cells) before the
first run.

## Configuring it

All settings live in **`dpsgd_optimization.yaml`** (validated by
`leakpro.schemas.PrivacyUtilityConfig`). The per-trial `audit.yaml` files are
generated by the run — they are output, not user input. The user-set
parameters:

| Setting | Meaning |
|---|---|
| `knobs` / `fixed` | which DP-SGD hyperparameters are searched, their bounds; pin any to a constant. Add an `epochs` knob to search epochs too. |
| `n_trials`, `seed`, `epochs` | search budget, reproducibility, training length |
| `delta` | the DP δ used for ε accounting — keep well below 1/n_target |
| `proxy_fpr` | the FPR the loop minimizes TPR at (0.0001, 0.001, 0.01 or 0.1) |
| `utility.metric` | `accuracy`, `balanced_accuracy`, or `auc`. Plain accuracy is only meaningful on class-balanced data (CIFAR-10 is); use the others for imbalanced tasks. |
| `utility.gate` | "did it learn" floor: at/below it the attack is skipped and the config is **pruned** (never on the frontier). `null` = the metric's chance level (auc: 0.5, others: 1/num_classes). |
| `rmia` | the RMIA attack block, passed verbatim into every generated audit config — any `AttackRMIA` parameter works here (`num_shadow_models`, `online`, `gamma`, `offline_a`, ...). |
| `splits` | population size, member (target-train) and nonmember/test sizes. `pop_size` must be exactly `2 * n_target` (see the shadow-model note above), and `n_test * proxy_fpr` must allow ≥ ~10 false positives or the run refuses to start. |

## Running it

```bash
# tiny end-to-end pipeline check (2 configs, small data)
python run_optimization.py --smoke

# a real run, settings from dpsgd_optimization.yaml
python run_optimization.py
python run_optimization.py --config my_settings.yaml
```

**Cost.** One configuration trains 1 target + `rmia.num_shadow_models` reference
models from scratch. The reference models are what make the attack real; they
are also the cost. Start with `--smoke`.

## Output

Everything lands in `output_dir` (default `leakpro_output/dpsgd_optimization`):

| File | What it is |
|---|---|
| `study.db` | the Optuna study (SQLite); rerunning the same command **resumes** it |
| `population.pkl` | the normalized CIFAR subset used as the audit population |
| `resolved_config.json` | the exact settings the run used (read by `validate_frontier.py`) |
| `trials/config_<hash>/` | per-configuration target, `dpsgd_dic.pkl`, audit config, RMIA outputs |
| `frontier.png` | scatter of every configuration with the Pareto front highlighted |

Resume is exact: rerun the same command and finished trials are read from
`study.db` — only the remaining trials run.

## Reading the results

The Pareto front is `study.best_trials`; each trial's `values` are
`(utility, TPR@1%)` and `trial.user_attrs` carries `epsilon` (the formal DP
budget) and the RMIA `roc_auc`. **Lower TPR is safer; higher utility is better.**

## Validating the frontier

The loop uses a modest number of reference models. Before trusting a frontier
point, re-audit it with a stronger attack (more references) — reusing the target
already trained during the campaign:

```bash
python validate_frontier.py --run-dir leakpro_output/dpsgd_optimization --n-shadow 16
```

This writes `validation.json` with TPR at 0.1% and 1% FPR for each frontier
point (`selection_bias` = how optimistic the loop was) and a `proxy_agreement`
check that ranking by TPR@1% agrees with ranking by TPR@0.1%.
